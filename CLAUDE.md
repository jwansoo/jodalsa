# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
npm install              # install dependencies
npm run dev               # start Vite dev server with HMR
npm run build              # type-check (vue-tsc) then production build
npm run type-check         # vue-tsc --build only
npm run lint                # runs lint:oxlint then lint:eslint (both --fix)
npm run format               # prettier --write on src/
npm run preview               # preview the production build

# Supabase (project ref bmchoackxtimxbqvncvd, local CLI project id "jodal-test")
npm run supabase:login      # authenticate the Supabase CLI
npm run supabase:link        # link this repo to the remote project
npm run db:migrate:new -- <name>   # create a new migration in supabase/migrations
npm run db:reset             # supabase db reset --linked
npm run db:seed              # node --env-file=.env database/seed.js (requires TESTING_USER_EMAIL, SERVICE_ROLE_KEY)
npm run supabase:types        # regenerate database/types.ts from the remote schema
```

There are no tests configured in this project (no test runner/dependency present).

To type-check or lint a single file, prefer running the underlying tool directly, e.g. `npx eslint src/path/to/File.vue --fix` or `npx oxlint src/path/to/File.vue --fix`.

### Environment variables

No `.env.example` is checked in; `.env` is gitignored. Required variables, inferred from usage:

- `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` — used by `src/lib/supabaseClient.ts` (client-side)
- `SERVICE_ROLE_KEY`, `TESTING_USER_EMAIL` — used by `database/seed.js` only (server-side, never expose `SERVICE_ROLE_KEY` client-side)

## Architecture

Vue 3 + Vite + TypeScript app backed by Supabase, with a Korean-language UI (`index.html` sets `lang="kr"` and forces dark mode via `class="dark"` on `<html>`). The app is a study/exam-prep platform for the "공공조달관리사" (public procurement manager) certification: a mock-exam runner, a question bank, and a visitor-inquiry chat feature.

- **Entry point**: `src/main.ts` creates the app, installs Pinia, Vue Router, the FormKit plugin (`formkit.config.ts`), and the `vue-meta` manager (`createMetaManager()`), imports `iconify-icon` for its side effect (registers the `<iconify-icon>` custom element), and mounts to `#app`.
- **Root layout**: `src/App.vue` renders `<metainfo></metainfo>` (required by `vue-meta` — see Head/meta tags below) and switches between `AuthLayout` and `GuestLayout` (both lazy-loaded via `defineAsyncComponent`) based on `!!authStore.user || route.path === '/'` — i.e. the home page always renders inside `AuthLayout` (it needs the sidebar/navbar chrome even for guests) while every other unauthenticated route falls back to `GuestLayout`. Inside the active layout it renders `AppErrorPage` instead of the router view whenever `errorStore.activeError` is set, otherwise renders `<RouterView>` inside `<Suspense timeout="0">` keyed by route name, with a loading spinner fallback. `onErrorCaptured` routes component errors into the error store; `onMounted` starts `useAuthStore().trackAuthChanges()` to listen for Supabase auth state changes.
- **Layouts** (`src/components/Layout/main/`): `AuthLayout.vue` renders `Sidebar` + `TopNavbar` + a page title bound to `usePageStore().pageData.title`, and `provide`s a `menuKey` (see `src/utils/injectionKeys.ts`) so `Sidebar` can toggle its own collapsed/expanded width; it also mounts `AppNewTest` (the "create new question" dialog), toggled via a local `testSheetOpen` ref that `Sidebar` flips through a `test-clicked` emit (from its `+` dropdown menu). `GuestLayout.vue` is just a centered full-height slot, used for `/login` and `/register`.
  - `Sidebar.vue` builds its nav links from `authStore.profile`: `문의관리` (inquiry management, `/admin/inquiries`) only appears when `profile.is_admin` is true; `문제모음` (`/jodalsa`, see below) is likewise admin-only, and the '+' menu's `Test` item (opens `AppNewTest`) is disabled for non-admins — both also enforced at the router-guard level (`/jodalsa*` redirects non-admins to `/` the same way `/admin/*` does), so hiding the links isn't purely cosmetic. `사용설명서` (user manual, `/manual` — deliberately outside the `/admin` prefix) is visible to every logged-in user, admin or not. `수험교재` (study materials) is a plain route link to `/materials` (`src/pages/materials/index.vue`) — protected like any other non-public route by the router guard, so an anonymous visitor is bounced to `/login` automatically. That page renders three sections: `필기` embeds `CourseTree.vue` (a collapsible chapter/subtitle tree driven by `src/utils/courseList.ts`'s `courseList`), while `핵심규정` and `실기` each embed a flat `FlatMaterialList.vue` driven by `courseList.ts`'s `coreRegulationList`/`practicalMaterialList`. Selecting any subtitle calls `courseMaterialSignedUrlQuery` (`src/utils/supaQuerys.ts`, wraps `supabase.storage.from(bucket).createSignedUrl(path, 60)`) and opens the signed URL in `CoursePdfViewer.vue` (`src/components/course/`, async-loaded since `pdfjs-dist` is heavy) — it renders every page to its own `<canvas>` client-side (with a 15s per-page render timeout guarding malformed PDFs) rather than using a `<iframe>`/native viewer, and disables the canvas context menu, so there's no built-in download/print affordance. Each subject in `courseList` maps 1:1 to a private Storage bucket (`jodal_subject_1`/`2`/`3`, plus `4`/`5` for practical/core-regulation materials), with each subtitle's file conventionally at `subtitle_<n>/subtitle_<n>.pdf`. The home page (`src/pages/index.vue`) has a `수험교재` shortcut card mirroring the `모의고사` card — both are plain `RouterLink`s to their page with the same hover-reveal "바로가기" affordance.
- **Head/meta tags**: `vue-meta` (v3 alpha) provides the auto-imported `useMeta()` composable (configured in `vite.config.ts`'s `AutoImport` plugin). Its plugin registers a component as `Metainfo`, so the template tag **must** be written lowercase as `<metainfo>` (already case-correct as-is — do not "fix" the casing) or it silently fails to resolve and no meta tags get injected. `useMeta()`'s payload must nest tag data under known keys (e.g. `meta: [{ name: 'description', content: '...' }]`, not flat `{ name, content }`) — only `title`, `meta`, `link`, `htmlAttrs`, `bodyAttrs`, etc. are recognized. Individual pages (e.g. `src/pages/jodalsa/index.vue`) call `useMeta()` themselves to override the page title/description.
- **Routing is file-based**: routes are generated from `src/pages/**` via Vue Router's built-in file-routes generator (the `VueRouter()` plugin from `vue-router/vite`, configured in `vite.config.ts`), producing `typed-router.d.ts` and the `vue-router/auto-routes` virtual module consumed by `src/router/index.ts`. Add new routes by adding files under `src/pages/` (e.g. `src/pages/foo/[id].vue` → `/foo/:id`), not by hand-editing a routes array. Dynamic routes read typed params via `useRoute('/foo/[id]').params` (see `src/pages/users/[username].vue`, `src/pages/admin/inquiries/[id].vue`).
  - `src/router/index.ts` has a global `beforeEach` guard: it calls `authStore.getSession()` on every navigation, redirects unauthenticated users to `/login` for any route other than `/` (public) or `/login`/`/register`, bounces authenticated users away from `/login`/`/register` back to `/`, and redirects any `/admin/*` route to `/` unless `authStore.profile?.is_admin` is true. There is no server-side (RLS) enforcement of admin-only access — see Supabase integration below.
  - `src/pages/[..catchAll].vue` is the router's not-found catch-all: it just calls `useErrorStore().setError({ error: ..., customCode: 404 })` so unmatched routes render through the normal `AppErrorPage` flow.
- **Auto-imports**: `unplugin-auto-import` auto-imports Vue/Vue Router APIs, Pinia's `defineStore`/`storeToRefs`/`acceptHMRUpdate`, and `vue-meta`'s `useMeta`, and scans `src/stores` so store composables (`useAuthStore()`, etc.) are available with no manual import. `unplugin-vue-components` auto-registers every `.vue` component (including `src/components/ui/*`, `Layout/*`, `AppError/*`, `AppNew/*`, `exam/*`, `inquiries/*`) as a global. Generated declaration files `auto-imports.d.ts` / `components.d.ts` should not be hand-edited — they regenerate on dev/build.
- **State (Pinia, setup-store style)** in `src/stores/`:
  - `auth.ts` (`useAuthStore`) — holds `user` and `profile` (from the `profiles` table, including `is_admin`), plus `getSession()`/`trackAuthChanges()`/`setAuth()`. This is the store the router guard and `App.vue` depend on. Both `user` and `profile` are populated asynchronously (Supabase session lookup + a `profiles` query), so any code deriving values from them at module/setup scope (e.g. a plain array literal in `<script setup>`) will see stale/null data — derive with `computed()` instead so it updates once the async data lands.
  - `error.ts` (`useErrorStore`) — holds `activeError`, normalizing plain strings, `Error`s, and Supabase `PostgrestError`s into a common shape (`setError`/`clearError`); drives whether `App.vue` shows `AppErrorPage`, which picks `AppErrorDevSection.vue` vs `AppErrorProdSection.vue` based on `import.meta.env.DEV` and clears the error on every route change (`router.afterEach`).
  - `page.ts` (`usePageStore`) — just `pageData.title`, set per-page and rendered as the layout's page heading.
  - `loaders/` — per-feature data-loading stores, each wrapping a Supabase query in `useMemoize` (VueUse) to cache results by key and including a `validateCache()` step that re-fetches in the background and invalidates the memoized entry if the data has changed. `loaders/jodalsa.ts` (`useJodalsaStore`) loads `yesang_tests` rows (the editable question bank). `loaders/tests.ts` (`useTestsStore`) loads `jadal_tests` rows by `round` for the timed mock-exam feature (see below).
- **Composables** (`src/composables/`) and **utils** (`src/utils/`) split: composables hold stateful, component-facing logic (`formErrors.ts`'s `useFormErrors` manages login/register form error state; `useCountdown.ts` is a generic start/stop/resume countdown timer that calls an `onExpire` callback, used to time each exam period in `ExamRunner.vue`), while utils hold stateless helpers and Supabase query builders reused across stores/pages (`supaAuth.ts` wraps sign up/in/out and inserts the matching `profiles` row on registration; `supaQuerys.ts` centralizes typed Supabase query builders — including the `inquiry_threads`/`inquiry_messages` and `test_results` queries; `examScoring.ts` has the shared pass/fail rule (`isExamPassed`: every subject ≥ 40, average ≥ 60); `courseList.ts` is the static syllabus data rendered by `CourseTree.vue`; `formValidations.ts` has plain client-side validators; `injectionKeys.ts` defines typed `provide`/`inject` keys like `menuKey`).
- **Two exam-related features share the `jadal_tests`/`yesang_tests` tables but serve different purposes**:
  - `src/pages/jodalsa/` (`index.vue`, `[id].vue`) is the editorial CRUD view over `yesang_tests`, restricted to admins (see `Sidebar.vue`/router-guard note above) — `[id].vue` renders every field through `AppInPlaceEditText` (`src/components/AppInPlaceEdit/`, a click-to-edit-in-place text field that commits on blur/Enter and reverts on Esc), calling `updateTest` from `useJodalsaStore` on each commit. New questions are created via `AppNewTest.vue` (`src/components/AppNew/`, mounted from `AuthLayout.vue`), a FormKit-based dialog that inserts into `yesang_tests`.
  - The actual timed mock exam lives in `src/components/exam/ExamRunner.vue` (over `jadal_tests`, selected by `round` via `useTestsStore`): it splits questions into three fixed periods (교시, 30/20/30 questions, time proportional to question count out of a 120-minute total) driven by `useCountdown`, renders each question with `ExamQuestion.vue`/`ExamResultQuestion.vue` (`src/components/exam/`), and computes pass/fail (`isExamPassed`) and weak-area analysis (grouped by question `subtitle`, sorted ascending by accuracy) entirely client-side once every period is submitted. When a logged-in user (`authStore.profile` set) finishes all periods, the result is upserted into `test_results` (`upsertTestResultQuery`, keyed on `username,round`) — anonymous users can still take the exam and see their score/analysis, it just isn't persisted. `ExamRunner` is reused in two places: `src/pages/tests/index.vue` (round picker + full exam, any round) and `src/pages/index.vue` (the home page embeds it pre-collapsed as a free 1회차 trial, via `:start-collapsed="true"`).
  - `src/pages/results/[id].vue` reads a profile's `test_results` (via `profileQuery` + `testResultsQuery`) and renders one card per completed round with pass/fail and the saved analysis text; `src/pages/results/index.vue` is still an empty stub (no "my results" landing page/listing yet).
- **Visitor inquiries / support chat**: backed by `inquiry_threads` (one row per visitor conversation: `name`, optional `contact`) and `inquiry_messages` (`sender` is `'visitor' | 'admin'`), both public-read/write per the current RLS policies, with `inquiry_messages` added to the `supabase_realtime` publication.
  - `src/components/inquiries/ChatWidget.vue` is a floating widget mounted on the home page (`src/pages/index.vue`) for anonymous visitors: it persists the active `thread_id` in `localStorage` (key `inquiry-thread-id`) so a returning visitor's conversation resumes, and subscribes to Postgres changes on `inquiry_messages` (filtered by `thread_id`) to append admin replies live.
  - `src/pages/admin/inquiries/index.vue` (thread list) and `[id].vue` (thread detail + reply form, also realtime-subscribed) are the admin-side views, gated by the router's `is_admin` check — but note the underlying tables have no RLS restriction tying rows to admin status, so the guard is UI-only.
  - `src/pages/manual.vue` (route `/manual`, open to any logged-in user — not under `/admin`) renders the checked-in `docs/user-guide.md` — a Korean end-user guide covering every feature above — by importing it raw (`?raw`) and parsing it with `marked`; editing that markdown file is the way to update this in-app manual, there's no separate CMS/editor for it.
- **Forms**: most forms (login/register) are hand-rolled with shadcn-vue `Input`/`Label` plus the `useFormErrors` composable and `formValidations.ts` for client-side checks, rather than FormKit. FormKit (`@formkit/vue`, configured in `formkit.config.ts` + generated theme `formkit.theme.ts`) is used by `AppNewTest.vue` (see above). `src/components/forms/` otherwise holds one generic field primitive still in production use, `BaseSelect.vue` (the round picker in `src/pages/tests/index.vue`).
- **Supabase integration**:
  - Client: `src/lib/supabaseClient.ts`, typed against the generated `Database` type in `database/types.ts` (regenerate via `npm run supabase:types`).
  - Schema/migrations live in `supabase/migrations/` and define: `jadal_tests`, `yesang_tests` (exam-question content), `profiles` (`id` FKs to `auth.users`, plus `is_admin boolean default false`), `test_results` (one row per `username`+`round`, unique constraint, holds per-period scores/average/analysis text), and `inquiry_threads`/`inquiry_messages` (see above). All tables have RLS enabled but with fully public (`using (true)`) policies for select/insert/update/delete — there is no row-level auth restriction anywhere, including for admin-only data, despite the app having a login flow and an `is_admin` flag; admin gating is enforced only client-side by the router guard. The one exception is Storage: the `jodal_subject_1`/`2`/`3` buckets (course-material PDFs) are private, gated by a real `to authenticated` Storage policy (`course_materials_storage_policy` migrations) — this is the only place server-side auth is actually enforced.
  - `database/seed.js` uses the service-role key to create/verify a test account and matching profile row; run via `npm run db:seed`.
- **UI components**: shadcn-vue (`components.json`: `new-york` style, `stone` base color, Lucide icons) generates primitives into `src/components/ui/`. Data tables use `@tanstack/vue-table`, wrapped by `src/components/ui/data-table/DataTable.vue`, with column definitions colocated under `src/utils/tableColumns/`.
- **Path alias**: `@/*` maps to `src/*` (configured in `vite.config.ts` and both `tsconfig.json`/`tsconfig.app.json`).
- **PWA**: `vite-plugin-pwa` (`generateSW` strategy, `registerType: 'autoUpdate'`) is configured in `vite.config.ts`, only active in production builds (`npm run dev` doesn't register a service worker). The manifest/icons (`public/pwa-192.png`, `public/pwa-512.png`, `public/apple-touch-icon.png`) let a mobile browser "add to home screen" and launch the site standalone (no browser chrome). Those three PNGs were generated by a one-off Node script (raw pixel buffer → hand-built PNG via `zlib.deflateSync`, no image library) rather than exported from a design tool — regenerate them the same way (or with a real image tool) if the icon design ever needs to change.
- **Linting**: two linters run in sequence — `oxlint` (fast, `correctness` category set to `error`) then `eslint` (Vue + TypeScript flat config in `eslint.config.ts`), with `eslint-plugin-oxlint` disabling ESLint rules oxlint already covers, and Prettier formatting rules turned off in ESLint (`eslint-config-prettier`) since Prettier owns formatting. `vue/multi-word-component-names` is disabled, so single-word component filenames (e.g. `Sidebar.vue`) are expected.
- **TypeScript**: project uses TS project references — `tsconfig.json` points to `tsconfig.app.json` (app source, extends `@vue/tsconfig/tsconfig.dom.json`) and `tsconfig.node.json` (build tooling config). `noUncheckedIndexedAccess` is enabled in the app config.
- **Formatting**: Prettier config has no semicolons, single quotes, 100-char print width (`.prettierrc.json`).
